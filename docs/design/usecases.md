# 유스케이스

> 시스템 경계: 백엔드 API. 화면 동작은 적지 않는다.
> 장소 검색 자체는 프론트가 카카오 SDK로 직접 수행하므로(원본 `src/lib/kakao.ts`) 백엔드 유스케이스가 아니다.
> 백엔드는 사용자가 검색 결과에서 장소를 **선택한 순간**부터 관여한다.

## 공통 규칙

> 유스케이스의 "규칙"에서는 아래 ID로 참조만 한다. 규칙을 바꿀 때는 이 절만 고친다.

### 회원
- **R-US-01** 닉네임은 NFC 정규화와 앞뒤 공백 제거(trim) 후 2자 이상 ~ 12자 이하(코드 포인트 기준)이며, 한글 완성형(가~힣)·영문 대소문자·숫자만 쓸 수 있다
- **R-US-02** 닉네임은 회원마다 유일하다. 비교는 대소문자를 구분하지 않고, 저장은 입력한 표기를 그대로 한다
  - 근거: `Nook`과 `nook`이 공존하면 화면에서 다른 회원을 구분하기 어렵다. 동시 가입·변경은 DB 제약이 최종 보장한다
  - 자기 닉네임의 대소문자만 바꾸는 변경(`nook` → `Nook`)은 허용한다. 구분이 어려워지는 다른 회원이 생기지 않기 때문이다. 표기까지 같은 닉네임으로의 변경은 아무것도 바꾸지 않고 성공한다(멱등)
- **R-US-03** 이메일은 앞뒤 공백 제거 후 1자 이상 254자 이하(코드 포인트 기준)이고, 공백이 없으며, `@`가 정확히 하나 있고 그 앞뒤가 비어 있지 않아야 한다. 회원마다 유일하며, 비교는 대소문자를 구분하지 않고 저장은 입력한 표기를 그대로 한다
  - 근거: 이메일 형식은 RFC 5322가 정하며 매우 복잡하므로 최소 조건만 검사한다(남이 정한 형식은 느슨하게). 실제로 쓸 수 있는 주소인지는 형식 검사가 아니라 메일 발송으로만 확인된다. 대소문자만 다른 주소는 대부분의 메일 서버에서 같은 수신함이므로 중복 가입으로 본다. 동시 가입은 DB 제약이 최종 보장한다

### 장소
- **R-PL-01** 카카오 장소 ID는 장소마다 유일하다
- **R-PL-02** 위도 -90~90, 경도 -180~180

### 북마크
- **R-BM-01** (회원, 장소) 북마크는 항상 0건 또는 1건이다
- **R-BM-02** 같은 (회원, 장소)에 저장과 해제가 겹치면, **커밋 순서상 나중 요청의 결과가 최종 상태**가 된다. 두 요청 모두 R-BM-01을 지키며 정상 응답한다
  - 근거: 어느 쪽이 이겨도 R-BM-01이 깨지지 않는다. 서버는 "동시"를 감지할 수 없고 처리 순서만 알 수 있다. 따라서 클릭 순서는 클라이언트 책임(응답 전 버튼 잠금 등)으로 두고 서버는 커밋 순서만 보장한다

### 별 상태 (R-STAR)
별 상태는 (회원, 장소)마다 **북마크 여부**와 **리뷰 작성 여부**의 조합으로 정해진다.

| 북마크 | 리뷰 | 별 상태 | 표시 |
|---|---|---|---|
| X | X | `empty` | 별이 표시되지 않는다 |
| O | X | `gray` | 회색별 |
| X | O | `fill` | 채운별 |
| O | O | `fill` | 채운별 |

### 리뷰
- **R-RV-01** 텍스트는 앞뒤 공백 제거(trim) 후 중간 공백 포함 10자 이상 ~ 50자 이하(코드 포인트 기준) 입력 가능
- **R-RV-02** 이미지는 최대 3장까지 업로드 가능
- **R-RV-03** 같은 회원은 같은 장소에 하루 1개까지 리뷰를 작성할 수 있다. 하루의 기준은 UTC 00:00(한국 시간 09:00)이다
  - 근거: 리뷰는 방문 기록이다(원본 명세 "1일 1회"). 기준 시간대는 서버 시간(UTC)으로 통일하고, 작성일은 Application이 정한 시각(`DateTimeOffset`)을 받아 Domain이 UTC 날짜로 계산한다. 동시 작성은 DB 제약이 최종 보장한다

### 좋아요
- **R-LK-01** (회원, 리뷰) 좋아요는 항상 0건 또는 1건이다

### 그룹 합류
- **R-GR-01** 그룹 정원은 4명이다
- **R-GR-02** 한 사용자가 동시 참여 가능한 그룹은 최대 3개이다
- **R-GR-03** 동시에 다른 사용자들이 추가 시 그룹 최대 인원이 넘는 상황이면, **먼저 추가된 사용자들이 최종 그룹원이 된다.** 그룹원 정원 이후 초과 요청 사용자들은 거절, 이미 그룹원 정원임을 안내
  - 근거: 서버는 "동시"를 감지할 수 없고 처리 순서만 알 수 있다. 그룹 합류는 선착순에 따른다.
- **R-GR-04** 한 사용자가 동시에 그룹 합류 요청 시 최대 참여 그룹 수가 넘는 상황이면, **먼저 시스템에 도착한 요청을 처리하는동안 해당 유저 행을 잠근다.** 이후 최대 그룹 수가 저장되면 다음 요청은 최대 그룹 수의 사용자는 거절 처리된다
  - 근거: 서버는 "동시"를 감지할 수 없고 처리 순서만 알 수 있다. 다른 그룹에 동시 요청한 것이므로 그룹 행을 잠가도 의미가 없고, 그룹 데이터 확인/처리 전에 사용자 데이터 잠금 후 확인한다.
- **R-GR-05** 초대 코드 형식: 대문자 A-Z(I·O 제외) 24자와 숫자 2-9 8자, 합쳐서 32개 문자 중 **6자**
- **R-GR-06** 초대 코드는 그룹마다 유일하다. 생성한 코드가 이미 쓰이고 있으면 새 코드로 다시 생성한다
- **R-GR-07** 같은 회원은 같은 그룹에 한 번만 참여할 수 있다. (회원, 그룹) 참여는 항상 0건 또는 1건이다
  - 이미 멤버인 회원의 합류 요청은 정원(R-GR-01)보다 먼저 중복으로 알린다. 회원이 바꿀 수 없는 더 구체적인 사실이며, 정원 초과로 알리면 자리가 날 때까지 의미 없는 재시도를 하게 된다
- **R-GR-08** 그룹을 만든 회원은 생성과 동시에 그 그룹의 첫 멤버가 된다
- **R-GR-09** 마지막 멤버가 그룹을 나가면 그룹도 같은 트랜잭션에서 삭제된다. 멤버가 0명인 그룹은 존재하지 않는다
  - 근거: 빈 그룹을 남겨 두면 살아 있는 초대 코드로 들어오는 합류와 정리 배치가 경합한다. 탈퇴와 그룹 삭제는 같은 Group 애그리거트의 DB 작업이라 한 트랜잭션으로 끝낼 수 있다
  - 동시성: 남은 두 멤버가 동시에 탈퇴하면 각자 "1명 남음"으로 판단해 빈 그룹이 남는다(Write Skew). 탈퇴도 합류(R-GR-03)와 같이 **인원을 세기 전에 그룹 행을 잠근다**
  - 멤버가 아닌 회원의 탈퇴 요청은 아무것도 바꾸지 않고 성공한다(멱등). 탈퇴를 연속 두 번 보냈을 때 성공과 실패를 함께 받는 혼란을 막는다
- **R-GR-10** 그룹명은 NFC 정규화와 앞뒤 공백 제거(trim) 후 2자 이상 ~ 6자 이하(코드 포인트 기준)이며, 한글 완성형(가~힣)·영문 대소문자·숫자·공백(U+0020)만 쓸 수 있다. 가운데 공백과 연속 공백은 허용한다. 그룹명은 그룹마다 유일하지 않다
  - 공백도 길이에 포함한다(예: "가    나"는 6자로 통과). 화면에서는 연속 공백이 하나로 보일 수 있다
  - 근거: 길이 단위·정규화는 닉네임(R-US-01)과 같다. 공백은 "주말 산책" 같은 이름을 위해 허용하되 ASCII 공백만 받아, 전각 공백·폭 없는 공백·한글 채움 문자(U+3164)로 보이지 않는 이름을 만드는 것을 화이트리스트로 막는다. 그룹은 초대 코드로 찾으므로 이름이 겹쳐도 구분에 문제가 없다
  - 이모지는 지금 허용하지 않는다. 허용 문자를 나중에 늘리는 변경은 기존 그룹명을 틀린 데이터로 만들지 않아 되돌리기 쉽다. 확장 시 코드 포인트와 화면 글자 수(그래핌)의 차이(예: 가족 이모지 1글자 = 5 코드 포인트)를 함께 정한다

### PL-01 선택한 장소를 확정한다  *(예시 — Claude 작성, 사용자 초안 SC-01을 고쳐 씀)*
- 액터: 회원
- 사전 조건: 로그인되어 있다. 프론트가 카카오 검색 결과 1건(카카오 장소 ID, 이름, 주소, 좌표)을 가지고 있다
- 기본 흐름
  1. 회원이 검색 결과 중 장소 하나를 선택해 보낸다
  2. 시스템이 같은 카카오 장소 ID로 등록된 장소가 있는지 확인한다
  3. 없으면 장소를 새로 등록하고, 있으면 기존 장소를 그대로 쓴다
  4. 시스템이 장소 정보와 그 장소의 리뷰 요약을 돌려준다
- 실패/대안 흐름
  - 1a. 필수 값(카카오 ID, 좌표)이 빠졌거나 좌표가 범위를 벗어남 → 거절, 어떤 값이 잘못됐는지 알린다
    - 빠짐(카카오 ID·좌표)과 카카오 ID 형식은 항상 검사한다. 좌표 범위·이름·주소는 **새 장소일 때만** 검사한다 — 기존 장소면 클라이언트 값을 쓰지 않고 저장된 값을 돌려주므로(덮어쓰지 않음, D5 결정)
  - 1b. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 3a. 두 회원이 아직 등록되지 않은 같은 장소를 동시에 선택함 → 장소는 1건만 생기고, 두 회원 모두 같은 장소를 받는다
- 규칙: R-PL-01, R-PL-02
- 사후 조건
  - 성공: 해당 카카오 ID의 장소가 정확히 1건 존재한다
  - 실패 시 보장: 장소가 생기지 않거나 기존 그대로다. 같은 카카오 ID로 중복된 장소가 생기지 않는다
- 메모: 원본 `upsertPlace`는 "조회 → 없으면 INSERT"를 두 번의 요청으로 나눠서 3a에서 경합이 생긴다(TOCTOU)



## 북마크

### BM-01 장소를 저장한다(북마크)
- 액터: 회원
- 사전 조건: 로그인되어 있다. 프론트가 카카오 검색 결과 1건(시스템 장소 ID)을 가지고 있다
- 기본 흐름
  1. 회원이 검색된 장소의 북마크 저장 요청을 보낸다
  2. 시스템이 이미 동일한 회원 ID로 북마크 했는지 확인한다
  3. 북마크 되어있지 않으면 장소를 북마크 처리하여 해당 장소는 규칙에 따라 별 상태를 계산한다
  4. 시스템이 북마크 처리 결과를 돌려준다
- 실패/대안 흐름
  - 1a. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 1b. 같은 회원이 저장 요청을 동시에 두 번 보냄 -> 동시성 처리하여 한 건은 성공 안내, 나머지 한 건은 이미 북마크 처리되었음 사실 안내
  - 1c. 같은 회원이 같은 장소에 저장과 해제(BM-02) 요청을 겹쳐 보냄 → R-BM-02
  - 2a. 이미 동일한 회원 ID로 해당 장소에 북마크 되어있다 -> 이미 되어있다는 사실 안내
  - 2b. 요청에 담긴 장소 ID가 DB에 없으면 → 거절, 유효하지 않은 장소로 인한 에러 발생 안내
- 규칙: R-STAR (저장 후 별은 리뷰가 없으면 `gray`, 있으면 `fill`)
- 사후 조건
  - 성공: DB에 사용자 ID, 장소 간 북마크 릴레이션 정보를 가진 릴레이션 데이터가 한 건 저장된다
  - 실패 시 보장: DB 에서 사용자 ID, 장소 간 북마크 정보를 가진 데이터가 생성되지 않는다

### BM-02 장소 저장을 해제한다
- 액터: 회원
- 사전 조건: 로그인되어 있다. 프론트가 카카오 검색 결과 1건(시스템 장소 ID)을 가지고 있다
- 기본 흐름
  1. 회원이 검색된 장소의 북마크 저장 해제 요청을 보낸다
  2. 시스템이 요청한 회원 ID로 이미 북마크 하지 않은 상태인지 확인한다
  3. 북마크가 되어있으면 장소를 북마크 해제 처리하여 해당 장소는 규칙에 따라 별 상태를 계산한다
  4. 시스템이 북마크 해제 처리 결과를 돌려준다
- 실패/대안 흐름
  - 1a. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 1b. 같은 회원이 저장 해제 요청을 동시에 두 번 보냄 -> 동시성 처리하여 한 건은 성공 안내, 나머지 한 건은 이미 북마크 해제 처리되었음 사실 안내
  - 1c. 같은 회원이 같은 장소에 저장(BM-01)과 해제 요청을 겹쳐 보냄 → R-BM-02
  - 2a. 이미 동일한 회원 ID로 해당 장소에 북마크 정보가 없다 -> 이미 해제 되어있다는 사실 안내
  - 2b. 요청에 담긴 장소 ID가 DB에 없으면 → 거절, 유효하지 않은 장소로 인한 에러 발생 안내
- 규칙: R-STAR (해제 후 별은 리뷰가 없으면 `empty`, 있으면 `fill` 유지)
- 사후 조건
  - 성공: DB에 사용자 ID, 장소 간 북마크 릴레이션 정보를 가진 릴레이션 데이터가 한 건 삭제된다
  - 실패 시 보장: DB 에서 사용자 ID, 장소, 북마크 정보를 가진 데이터가 삭제되지 않는다

### RV-02 리뷰를 수정한다
- 액터: 회원
- 사전 조건: 로그인되어 있다. 현재 사용자가 이전에 작성한 리뷰 ID를 가지고 있다.
- 기본 흐름
  1. 리뷰를 수정하고 저장 요청을 보낸다. 요청에는 본문, **남길 기존 이미지 ID**, 새 이미지가 최종 순서대로 담긴다 *(Claude 보완)*

  3. 시스템이 수정 요청이 유효한지 검증한다
  4. 시스템이 요청받은 리뷰 ID로 DB에서 조회한다
  5. 시스템이 리뷰에 새로 첨부된 이미지를 스토리지에 업로드한다
  6. 시스템이 요청받은 수정된 리뷰 컨텐츠, 추가된 이미지 스토리지 키, 이미지 순서로 DB 기존 리뷰 행을 수정한다

- 실패/대안 흐름
  - 1a. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 2a. 최소 글자 수보다 적거나, 최대 글자 수보다 많음 → 거절, 최소 & 최대 글자 수 안내

  - 3c. 남길 기존 이미지 수 + 새 이미지 수가 최대 장수 초과 → 거절, 최대 n장까지 첨부할 수 있다고 안내 (R-RV-02) *(Claude 수정: 요청의 새 이미지만이 아니라 합계로 판단)*
  - 4a. 리뷰가 DB에 존재하지 않음 → 거절, 존재하지 않는 리뷰임을 안내
  - 4b. 조회 리뷰의 유저 ID와 요청 ID와 다름 → 거절(403), 본인 리뷰만 수정 가능함을 안내 *(403: 리뷰는 PL-02에서 공개되는 정보라 존재를 숨길 이유가 없다, 2026-10-23 사용자 결정)*
  - 4c. 남길 기존 이미지 ID가 이 리뷰의 이미지가 아님 → 거절, 유효하지 않은 이미지 안내 *(Claude 추가: 3c의 합계는 요청만으로 계산하지만, ID가 진짜인지는 조회 뒤에야 안다)*
  - 5a. 이미지의 스토리지 키값 길이가 최대 길이 초과 → 거절, 스토리지 키 생성은 서버단 문제이므로, 서버 예외로 안내
  - 5b. 이미지의 순서(sortOrder) 값이 음수 → 거절, 이미지 순서 인덱스 지정은 서버단 문제이므로, 서버 예외로 안내
  - 5c. 스토리지에 이미지 업로드 실패 → 거절, 이미지 업로드 실패 에러 안내
  - 6a. DB 업데이트 실패 → 거절, 서버단 문제이므로, 서버 예외로 안내
  - 6b. 4단계 조회 뒤 같은 리뷰가 삭제됨(RV-03 커밋) → 4a와 같은 안내(존재하지 않는 리뷰). `reviews` UPDATE 0행 또는 `review_images` INSERT의 FK 위반(23503)으로 드러난다. 새로 올린 이미지는 정리 배치 대상 *(Claude 추가)*
  - 6c. 4단계 조회 뒤 같은 리뷰를 다른 수정 요청이 먼저 커밋해 이미지 구성이 바뀜 → 거절(409), 다시 불러온 뒤 수정하라고 안내. 저장 트랜잭션은 리뷰 행을 먼저 잠그고(`FOR UPDATE`), `reviews.version`(낙관적 동시성 토큰)이 읽은 값과 다르면 0행 → 409. 본문만 바꾼 수정끼리도 감지한다. 빠질 이미지는 지우지 않고, 새로 올린 이미지는 정리 배치 대상 *(2026-10-24 사용자 결정: 404와 구분, 행 잠금 + version — incident 002)*
- 규칙: 
  - R-RV-01
  - R-RV-02
  - R-STAR (저장 여부와 상관없이 fill)
- 사후 조건
  - 성공: DB의 수정 요청한 리뷰의 리뷰 데이터가 한 건 수정된다
    - 요청에 없는 기존 이미지는 `review_images`에서 삭제된다. 스토리지 파일은 **커밋 후** 지우고, 실패하면 정리 배치가 잡는다(RV-01 확정 사항) *(Claude 추가)*
  - 실패 시 보장: 
    - 유저, 리뷰 컨텐츠, 이미지 정보 등이 유효하지 않거나 제한에 걸리면 이미지가 생성되지 않고, DB 데이터가 수정 되지 않는다
    - 스토리지에 이미지 업로드 실패 시에는 이미지는 노출되지 않고 추후 정리된다. DB 데이터는 생성되지 않는다
    - 이미지 업로드 정상 후 DB 저장 실패 시에는, DB 데이터는 수정되지 않지만, 스토리지에 이미지는 남아 있으므로 정리 배치로 지운다
    - DB 저장 실패(롤백) 시 기존 이미지는 그대로 참조되므로 배치가 지우지 않는다. 스토리지 파일을 커밋 전에 지우지 않는 이유다 *(Claude 추가)*

### RV-03 리뷰를 삭제한다
- 액터: 회원
- 사전 조건: 로그인되어 있다. 현재 사용자가 이전에 작성한 리뷰 ID를 가지고 있다.
- 기본 흐름
  1. 리뷰 삭제 요청을 보낸다. 요청에는 리뷰 ID가 담긴다
  2. 시스템이 리뷰 ID와 회원 ID가 **모두 맞는** 리뷰를 한 문장으로 삭제하고, 영향 행 수를 본다 *(C안, 2026-10-23 사용자 결정)*
  3. 0행이면 그 리뷰 ID가 아직 있는지 다시 조회한다(0행의 이유를 가리기 위해서만 — 판정은 2단계 영향 행 수)
  4. `200`으로 돌려준다. 본문: `changed`(이번 요청이 지웠는가), `star`(1행이면 `RETURNING place_id`로 이 회원·장소의 별을 계산, 0행이면 `null` — 지워진 행에서 장소를 알 수 없다. 프론트는 `changed=false`면 별을 갱신하지 않는다, ①안 사용자 결정)
- 실패/대안 흐름
  - 1a. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 3a′. 0행 + 리뷰 없음(이미 삭제·없는 ID·더블클릭·재시도) → **성공**, `changed=false`, `star=null` (멱등 — LK-01과 같은 방식)
  - 3b′. 0행 + 리뷰 있음(남의 리뷰) → 거절(403), 본인 리뷰만 삭제 가능함을 안내 (RV-02 4b와 같은 결정)
  - 3a. DB 리뷰 삭제 실패 → 거절, 서버단 문제이므로, 서버 예외로 안내
  - 3c. 같은 회원이 삭제를 동시에 두 번 보냄 → 둘째 DELETE는 첫째의 행 잠금을 기다린 뒤 0행 → 3a′(성공, `changed=false`). 재조회와 삭제 사이의 틈은 "아무것도 안 지웠는데 성공"으로만 잘못 분류될 수 있어 무해하다 *(Claude 추가)*
- 규칙: 
  - R-STAR: 삭제 후 이 회원이 이 장소에 남긴 리뷰가 **0개**면 북마크 여부에 따라 `gray`(저장)·`empty`(미저장), **1개 이상**이면 `fill` 유지 *(Claude 수정)*
  - R-RV-03과의 관계: 오늘 쓴 리뷰를 지우면 오늘 다시 쓸 수 있다(UNIQUE가 남은 행만 본다). **미결 — 원본 PM과 확인 필요** *(Claude 추가)*
- 사후 조건
  - 성공: DB의 삭제 요청한 리뷰의 리뷰 데이터가 한 건, 그 리뷰의 리뷰_이미지 데이터가 모두 삭제된다
    - 리뷰 이미지의 스토리지 파일은 **커밋 후** 지운다. 실패하면 정리 배치가 잡는다(RV-01 확정 사항). 커밋 전에는 지우지 않는다
    - 그 리뷰의 좋아요도 함께 삭제된다(`fk_likes_reviews` ON DELETE CASCADE) *(Claude 추가)*
  - 실패 시 보장: 
    - 리뷰 및 이미지 DB 데이터와 스토리지 이미지가 삭제 되지 않는다

- 실패/대안 흐름
  - 1a. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 2a. 초대 코드가 유효하지 않으면 → 거절, 유효하지 않은 코드로 인한 에러 발생 안내
  - 3a. 인증 토큰(JWT)에 담긴 사용자 ID가 DB에 없으면 → 거절, 유효하지 않은 사용자로 인한 에러 발생 안내
  - 3b. 요청에 담긴 사용자가 이미 3개 그룹에 참여 중이면 → R-GR-02 규칙(거절, 이미 최대 그룹 수 참가 중 안내)
  - 4a. 요청에 담긴 사용자가 이미 그룹에 있으면 → 거절, 이미 포함된 그룹임을 안내
  - 4b. 이미 인원이 모두 찬 상태인 그룹이면 → R-GR-01 규칙(거절, 이미 이미 그룹원 정원임을 안내)
  - 4c. 초대코드로 식별된 그룹 ID가 DB에 없으면 → 거절, 유효하지 않은 그룹으로 인한 에러 발생 안내
  - 5a. 현재 2개 그룹 참여 중인 사용자가 동시에 다른 두 그룹에 합류 요청하면 → R-GR-04 규칙(거절, 이미 최대 그룹 수 참가 중 안내)
  - 5b. 동시에 다른 사용자들이 추가 시 그룹 최대 인원이 넘는 상황이면 → R-GR-03 규칙
- 규칙
  - R-GR-01
  - R-GR-02
  - R-GR-03
  - R-GR-04
  - R-GR-05
- 사후 조건
  - 성공:
    - 사용자는 요청한 그룹에 합류한다
    - 그룹원들의 장소 저장 정보들을 사용자에게 퍼블리싱한다
  - 실패 시 보장: 
    - 사용자, 그룹이 유효하지 않거나 제한에 걸리면 그룹 멤버 데이터가 생성되지 않는다
  - 불변식 (동시 요청이 몇 개가 오든, 성공·실패와 상관없이 항상 참) *(Claude 작성)*
    - 한 그룹의 멤버는 **4명 이하**다 (R-GR-01)
    - 한 사용자가 참여한 그룹은 **3개 이하**다 (R-GR-02)
    - (사용자, 그룹) 멤버 데이터는 **0건 또는 1건**이다
