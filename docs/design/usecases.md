# 유스케이스

> 시스템 경계: 백엔드 API. 화면 동작은 적지 않는다.
> 장소 검색 자체는 프론트가 카카오 SDK로 직접 수행하므로(원본 `src/lib/kakao.ts`) 백엔드 유스케이스가 아니다.
> 백엔드는 사용자가 검색 결과에서 장소를 **선택한 순간**부터 관여한다.

## 공통 규칙

> 유스케이스의 "규칙"에서는 아래 ID로 참조만 한다. 규칙을 바꿀 때는 이 절만 고친다.

### 장소
- **R-PL-1** 카카오 장소 ID는 장소마다 유일하다
- **R-PL-2** 위도 -90~90, 경도 -180~180

### 북마크
- **R-BM-1** (회원, 장소) 북마크는 항상 0건 또는 1건이다
- **R-BM-2** 같은 (회원, 장소)에 저장과 해제가 겹치면, **나중에 처리된 요청의 결과가 최종 상태**가 된다. 두 요청 모두 R-BM-1을 지키며 정상 응답한다
  - 근거: 어느 쪽이 이겨도 R-BM-1이 깨지지 않는다. 서버는 "동시"를 감지할 수 없고 처리 순서만 알 수 있다. 사용자의 마지막 동작이 의도에 가깝다

### 별 상태 (R-STAR)
별 상태는 (회원, 장소)마다 **북마크 여부**와 **리뷰 작성 여부**의 조합으로 정해진다.

| 북마크 | 리뷰 | 별 상태 | 표시 |
|---|---|---|---|
| X | X | `empty` | 별이 표시되지 않는다 |
| O | X | `gray` | 회색별 |
| X | O | `fill` | 채운별 |
| O | O | `fill` | 채운별 |

### 리뷰
- **R-RV-1** 텍스트는 공백 포함 10자 이상 ~ 50자 이하 입력 가능
- **R-RV-2** 이미지는 최대 3장까지 업로드 가능

### 그룹 합류
- **R-GR-01** 그룹 정원은 4명이다
- **R-GR-02** 한 사용자가 동시 참여 가능한 그룹은 최대 3개이다
- **R-GR-03** 동시에 다른 사용자들이 추가 시 그룹 최대 인원이 넘는 상황이면, **먼저 추가된 사용자들이 최종 그룹원이 된다.** 그룹원 정원 이후 초과 요청 사용자들은 거절, 이미 그룹원 정원임을 안내
  - 근거: 서버는 "동시"를 감지할 수 없고 처리 순서만 알 수 있다. 그룹 합류는 선착순에 따른다.
- **R-GR-04** 한 사용자가 동시에 그룹 합류 요청 시 최대 참여 그룹 수가 넘는 상황이면, **먼저 시스템에 도착한 요청을 처리하는동안 해당 유저 행을 잠근다.** 이후 최대 그룹 수가 저장되면 다음 요청은 최대 그룹 수의 사용자는 거절 처리된다
  - 근거: 서버는 "동시"를 감지할 수 없고 처리 순서만 알 수 있다. 다른 그룹에 동시 요청한 것이므로 그룹 행을 잠가도 의미가 없고, 그룹 데이터 확인/처리 전에 사용자 데이터 잠금 후 확인한다.
- **R-GR-05** 초대 코드 형식: 대문자 A-Z(I·O 제외) 24자와 숫자 2-9 8자, 합쳐서 32개 문자 중 **6자**

### PL-01 선택한 장소를 확정한다  *(예시 — Claude 작성, 사용자 초안 SC-01을 고쳐 씀)*
- 액터: 회원
- 사전 조건: 로그인되어 있다. 프론트가 카카오 검색 결과 1건(카카오 장소 ID, 이름, 주소, 좌표)을 가지고 있다
- 기본 흐름
  1. 회원이 검색 결과 중 장소 하나를 선택해 보낸다
  2. 시스템이 같은 카카오 장소 ID로 등록된 장소가 있는지 확인한다
  3. 없으면 장소를 새로 등록하고, 있으면 기존 장소를 그대로 쓴다
  4. 시스템이 장소 정보와 그 장소의 리뷰 요약을 돌려준다
- 실패/대안 흐름
  - 1a. 필수 값(카카오 ID, 좌표)이 빠졌거나 좌표가 범위를 벗어남 → 거절, 어떤 값이 잘못됐는지 알린다
  - 1b. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 3a. 두 회원이 아직 등록되지 않은 같은 장소를 동시에 선택함 → 장소는 1건만 생기고, 두 회원 모두 같은 장소를 받는다
- 규칙: R-PL-1, R-PL-2
- 사후 조건
  - 성공: 해당 카카오 ID의 장소가 정확히 1건 존재한다
  - 실패 시 보장: 장소가 생기지 않거나 기존 그대로다. 같은 카카오 ID로 중복된 장소가 생기지 않는다
- 메모: 원본 `upsertPlace`는 "조회 → 없으면 INSERT"를 두 번의 요청으로 나눠서 3a에서 경합이 생긴다(TOCTOU)



## 북마크

### BM-01 장소를 저장한다(북마크)
- 액터: 회원
- 사전 조건: 로그인되어 있다. 프론트가 카카오 검색 결과 1건(시스템 장소 ID)을 가지고 있다
- 기본 흐름
  1. 회원이 검색된 장소의 북마크 저장 요청을 보낸다
  2. 시스템이 이미 동일한 회원 ID로 북마크 했는지 확인한다
  3. 북마크 되어있지 않으면 장소를 북마크 처리하여 해당 장소는 규칙에 따라 별 상태를 계산한다
  4. 시스템이 북마크 처리 결과를 돌려준다
- 실패/대안 흐름
  - 1a. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 1b. 같은 회원이 저장 요청을 동시에 두 번 보냄 -> 동시성 처리하여 한 건은 성공 안내, 나머지 한 건은 이미 북마크 처리되었음 사실 안내
  - 1c. 같은 회원이 같은 장소에 저장과 해제(BM-02) 요청을 겹쳐 보냄 → R-BM-2
  - 2a. 이미 동일한 회원 ID로 해당 장소에 북마크 되어있다 -> 이미 되어있다는 사실 안내
  - 2b. 요청에 담긴 장소 ID가 DB에 없으면 → 거절, 유효하지 않은 장소로 인한 에러 발생 안내
- 규칙: R-STAR (저장 후 별은 리뷰가 없으면 `gray`, 있으면 `fill`)
- 사후 조건
  - 성공: DB에 사용자 ID, 장소 간 북마크 릴레이션 정보를 가진 릴레이션 데이터가 한 건 저장된다
  - 실패 시 보장: DB 에서 사용자 ID, 장소 간 북마크 정보를 가진 데이터가 생성되지 않는다

### BM-02 장소 저장을 해제한다
- 액터: 회원
- 사전 조건: 로그인되어 있다. 프론트가 카카오 검색 결과 1건(시스템 장소 ID)을 가지고 있다
- 기본 흐름
  1. 회원이 검색된 장소의 북마크 저장 해제 요청을 보낸다
  2. 시스템이 요청한 회원 ID로 이미 북마크 하지 않은 상태인지 확인한다
  3. 북마크가 되어있으면 장소를 북마크 해제 처리하여 해당 장소는 규칙에 따라 별 상태를 계산한다
  4. 시스템이 북마크 해제 처리 결과를 돌려준다
- 실패/대안 흐름
  - 1a. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 1b. 같은 회원이 저장 해제 요청을 동시에 두 번 보냄 -> 동시성 처리하여 한 건은 성공 안내, 나머지 한 건은 이미 북마크 해제 처리되었음 사실 안내
  - 1c. 같은 회원이 같은 장소에 저장(BM-01)과 해제 요청을 겹쳐 보냄 → R-BM-2
  - 2a. 이미 동일한 회원 ID로 해당 장소에 북마크 정보가 없다 -> 이미 해제 되어있다는 사실 안내
  - 2b. 요청에 담긴 장소 ID가 DB에 없으면 → 거절, 유효하지 않은 장소로 인한 에러 발생 안내
- 규칙: R-STAR (해제 후 별은 리뷰가 없으면 `empty`, 있으면 `fill` 유지)
- 사후 조건
  - 성공: DB에 사용자 ID, 장소 간 북마크 릴레이션 정보를 가진 릴레이션 데이터가 한 건 삭제된다
  - 실패 시 보장: DB 에서 사용자 ID, 장소, 북마크 정보를 가진 데이터가 삭제되지 않는다

## 리뷰

### RV-01 리뷰를 작성한다
- 액터: 회원
- 사전 조건: 로그인되어 있다. 프론트가 카카오 검색 결과 1건(시스템 장소 ID)을 가지고 있다
- 기본 흐름
  1. 리뷰를 작성하고 저장 요청을 보낸다
  2. 시스템이 장소, 리뷰 컨텐츠 유효성을 검증한다
  3. 시스템이 리뷰에 첨부된 이미지를 스토리지에 업로드한다
  4. 이미지 정상 업로드 후, 시스템이 요청받은 회원 ID, 장소 ID, 리뷰 컨텐츠, 이미지 URL(또는 리뷰 + 이미지 키를 DB) 데이터를 DB에 저장한다
  5. 저장 시 성공 안내한다
- 실패/대안 흐름
  - 1a. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 2a. 요청에 담긴 장소 ID가 DB에 없으면 → 거절, 유효하지 않은 장소로 인한 에러 발생 안내
  - 2b. 리뷰 최소/최대 글자 수를 벗어남 → 거절, 작성 가능 글자 수 범위 안내
  - 2c. 리뷰 최대 첨부 이미지 수를 벗어남 → 거절, 첨부 가능 이미지 수 안내
  - 3a. 스토리지에 이미지 업로드 실패 → 거절, 이미지 업로드 실패 에러 안내
- 규칙: 
  - R-RV-1
  - R-RV-2
  - R-STAR (저장 여부와 상관없이 fill)
- 사후 조건
  - 성공: DB에 사용자 ID, 장소, 리뷰 데이터가 한 건 생성된다
  - 실패 시 보장: 
    - 장소, 리뷰 컨텐츠 유효하지 않거나 제한에 걸리면 이미지와 DB데이터 모두 생성되지 않는다
    - 스토리지에 이미지 업로드 실패 시에는 이미지는 노출되지 않고 추후 정리된다. DB 데이터는 생성되지 않는다
    - 이미지 업로드 정상 후 DB 저장 실패 시에는, DB 데이터 모두 생성되지 않지만, 스토리지에 이미지는 남아 있으므로 정리 배치로 지운다

## 그룹

### GR-01 초대 코드로 그룹에 합류한다
- 액터: 회원
- 사전 조건: 로그인되어 있다. 그룹을 생성한 사용자에게로부터 초대 코드를 받았다.
- 기본 흐름
  1. 사용자는 전달받은 초대 코드로 그룹 합류를 요청한다
  2. 시스템이 초대 코드가 자릿수 등이 유효한지 검증한다
  3. 시스템이 요청 사용자가 유효한지 확인한다 
  4. 시스템이 초대 코드로 그룹을 식별하여, 해당 그룹이 유효한지 확인한다
  5. 초대 요청 사용자 ID와 그룹 ID 간 릴레이션 데이터를 DB에 저장한다
  6. 저장 시 그룹 합류 성공 안내한다
- 실패/대안 흐름
  - 1a. 로그인 토큰이 없거나 만료됨 → 거절, 재인증 요구
  - 2a. 초대 코드가 유효하지 않으면 → 거절, 유효하지 않은 코드로 인한 에러 발생 안내
  - 3a. 인증 토큰(JWT)에 담긴 사용자 ID가 DB에 없으면 → 거절, 유효하지 않은 사용자로 인한 에러 발생 안내
  - 3b. 요청에 담긴 사용자가 이미 3개 그룹에 참여 중이면 → R-GR-02 규칙(거절, 이미 최대 그룹 수 참가 중 안내)
  - 4a. 요청에 담긴 사용자가 이미 그룹에 있으면 → 거절, 이미 포함된 그룹임을 안내
  - 4b. 이미 인원이 모두 찬 상태인 그룹이면 → R-GR-01 규칙(거절, 이미 이미 그룹원 정원임을 안내)
  - 4c. 초대코드로 식별된 그룹 ID가 DB에 없으면 → 거절, 유효하지 않은 그룹으로 인한 에러 발생 안내
  - 5a. 현재 2개 그룹 참여 중인 사용자가 동시에 다른 두 그룹에 합류 요청하면 → R-GR-04 규칙(거절, 이미 최대 그룹 수 참가 중 안내)
  - 5b. 동시에 다른 사용자들이 추가 시 그룹 최대 인원이 넘는 상황이면 → R-GR-03 규칙
- 규칙
  - R-GR-01
- 사후 조건
  - 성공:
    - 사용자는 요청한 그룹에 합류한다
    - 그룹원들의 장소 저장 정보들을 사용자에게 퍼블리싱한다
  - 실패 시 보장: 
    - 사용자, 그룹이 유효하지 않거나 제한에 걸리면 그룹 멤버 데이터가 생성되지 않는다
