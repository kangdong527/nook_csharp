# 배포 후 변경 가이드 (디자인·기능)

> 배경: PM이 화면 디자인을 손보고 싶어 하고, 그룹원 보기(X2) 같은 기능 추가도 남아 있다. DEP(배포)가 끝난 **뒤에** 이 작업을 해도 되는지, 하려면 무엇을 지켜야 하는지 정리한다.

## 1. 결론

배포를 먼저 끝내고 그 뒤에 디자인과 기능을 바꿔도 된다. 오히려 **8단계 CD가 끝난 뒤가 더 편하다.** 그때부터는 PR을 병합하면 빌드, 배포, 헬스체크가 자동으로 돌고, 실패하면 직전 버전으로 돌아간다. CD 전에 바꾸면 배포할 때마다 손으로 해야 한다.

```
지금 ── 5단계 D·E ── 8단계 CD ── 9·10단계 ── 디자인·기능 수정(PR마다 자동 배포) ── 공개
                                    ↑
                      PM 디자인 작업은 이 사이에 병행
```

공개 시점은 배포와 따로 정한다. 배포를 마쳐도 **443(앱)은 개발자 IP에만 열려 있다**(dep-plan 결정 6). 공개는 SG 규칙 하나를 바꾸는 일이다.

## 2. 왜 배포 후 수정이 안전한가 — 롤백의 범위

`deploy/scripts/deploy.sh`는 배포가 실패하면 **컨테이너 이미지만** 직전 버전으로 되돌린다. **DB는 되돌리지 않는다.**

| 변경 종류 | 예 | 롤백 | 위험도 |
|---|---|---|---|
| 화면만 | 색, 레이아웃, 문구, 아이콘 | 완전히 되돌아감 | 낮음 |
| 조회 API 추가(스키마 변경 없음) | X2 그룹원 보기 | 완전히 되돌아감 | 낮음 |
| 쓰기 로직 변경(스키마 변경 없음) | 규칙·검증 수정 | 이미지만 되돌아감. 그사이 저장된 데이터는 남음 | 중간 |
| **DB 스키마 변경** | 컬럼 추가·삭제·이름 변경, 제약 변경 | **DB는 그대로** → 직전 코드가 새 스키마에서 돌아야 함 | **높음** |

## 3. 디자인 변경 시 주의

| 항목 | 내용 | PM에게 필요한 것 |
|---|---|---|
| **외부 폰트·이미지·CDN** | 운영 서버는 CSP(콘텐츠 보안 정책)를 **강제 모드**로 켜 두었다(`deploy/Caddyfile`). 허용 목록에 없는 외부 주소는 브라우저가 **오류 표시 없이 막는다.** 지금 허용된 외부 출처는 카카오 지도 관련 도메인과 `cdn.jsdelivr.net`(스타일·폰트)뿐이다 | 새 폰트나 외부 이미지를 쓸 때 **미리 알려 주기**. 파일을 `web/` 안에 직접 넣으면 CSP를 바꾸지 않아도 된다 |
| 로컬과 운영 차이 | `npm run dev`에는 CSP가 없다. 막힘은 compose(운영과 같은 구성)로 띄워야 보인다 | 개발자가 compose로 확인한다 |
| 회귀 확인 | `web/`에는 아직 자동 테스트가 없다(incident 004 미결). 화면을 크게 바꾸면 `fe-manual-checklist.md`로 손 확인을 한 번 돌린다 | 확인 결과를 같이 본다 |
| 그룹 색 | 지금 그룹 색 슬롯 0~3은 **임시 팔레트**다(`slotColor`, 디자인 대기). 이번 디자인에서 정하면 FE 매핑만 바꾸면 된다 | 색 4개 확정 |
| 처리방침·수집 동의 화면 | 공개 조건(7단계)에 들어가는 화면이다. 이 화면도 다시 디자인하면 공개 시점과 맞춘다 | 범위에 포함할지 결정 |

## 4. 기능 변경 시 주의

### 4.1 공통

1. **유스케이스 먼저.** 누가, 무엇을, 실패하면 어떻게 되는지를 먼저 정한다(`usecases.md`).
2. **인가.** 다른 사람의 데이터를 읽는 API는 "요청한 사람이 볼 자격이 있는가"를 서버가 확인한다. 빠뜨리면 ID만 바꿔서 남의 정보를 보는 사고(IDOR)가 난다.
3. **개인정보 노출 범위.** 응답에 넣는 필드는 처리방침의 이용 목적 안에서만 넣는다. 이메일, 성별, 생일은 다른 회원에게 보여 주지 않는다.
4. **BFF 허용 목록.** 화면은 C# API를 직접 부르지 않고 `web/`의 중계(`/api/nook/[...path]`)를 거친다. 이 중계는 허용 목록 방식이라, 새 API 경로를 한 줄 추가해야 한다.

### 4.2 DB 스키마를 바꿔야 할 때: 확장 → 전환 → 축소

롤백이 DB를 되돌리지 않으므로, 한 번의 배포로 스키마와 코드를 함께 바꾸지 않는다.

| 단계 | 하는 일 | 이 단계에서 롤백하면 |
|---|---|---|
| ① 확장 | 새 컬럼·테이블을 **추가만** 한다(옛 것 유지) | 옛 코드가 그대로 동작 |
| ② 전환 | 코드가 새 구조를 쓰도록 배포 | ①이 남아 있어 안전 |
| ③ 축소 | 옛 컬럼을 지운다(다음 배포) | 옛 코드로 돌아갈 일이 없을 때만 |

공개 전에는 실제 회원 데이터가 없어서 이 규칙을 어겨도 티가 나지 않는다. **공개 뒤에는 반드시 지킨다.** 그래서 스키마를 크게 바꾸는 기능은 공개 **전에** 넣는 편이 비용이 적다.
