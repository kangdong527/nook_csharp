## 3. 솔루션 구조 (D1에 사용자가 `dotnet new`로 직접 만든다)

```
nook_csharp/
├─ src/
│  ├─ Nook.Domain/          엔티티·값 객체·도메인 규칙 (외부 의존 0)
│  ├─ Nook.Application/     유스케이스, 트랜잭션 경계
│  ├─ Nook.Infrastructure/  EF Core DbContext, 마이그레이션, Redis
│  ├─ Nook.Api/             컨트롤러, DI, 미들웨어
│  └─ Nook.Algorithms/      직접 구현한 자료구조 (Geohash, LRU, TokenBucket ...)
├─ tests/
│  ├─ Nook.Domain.Tests/
│  ├─ Nook.Integration.Tests/   Testcontainers(PostgreSQL)
│  └─ Nook.Algorithms.Tests/
├─ benchmarks/Nook.Benchmarks/
├─ load/                    k6 스크립트
├─ deploy/                  Dockerfile, docker-compose, Caddyfile
└─ docs/
   ├─ 개발_프로세스.md      (이 문서)
   ├─ progress.md           매일 갱신
   ├─ learning-log.md       매일 3줄
   ├─ design/               유스케이스·ERD·API 명세 (사용자 작성)
   ├─ adr/                  설계 결정 기록
```

계층 의존은 `Api → Application → Domain`, `Infrastructure → Application/Domain`의 한 방향이다. 이 구조를 그대로 쓸지는 D1 ADR에서 사용자가 정한다.

**D8 · 대용량 데이터와 인덱스 튜닝 ★**
- 시드: 장소 100만, 리뷰 1,000만, 좋아요 수천만 (`COPY` 또는 `generate_series`, 스크립트는 Claude 작성 가능)

- 인덱스 설계: 복합 인덱스 순서, 커버링 인덱스(`INCLUDE`), geohash 컬럼 vs PostGIS GiST(D7 구현과 비교)

- 🚦 게이트: **incident 002**(인덱스), **003**(페이지네이션)
- 🚀 운영 반영: 시드는 로컬에서만. 채택한 인덱스를 운영 DB에 `CREATE INDEX CONCURRENTLY` 마이그레이션으로 무중단 추가(EF 마이그레이션 트랜잭션과 부딪히는 지점 기록), Keyset 피드는 프론트와 같은 PR로 교체

**D9 · 쿼리 튜닝과 ORM 이해**
- EF Core가 만드는 SQL을 로그로 확인하고 N+1을 찾는다. `AsNoTracking`, projection, split query, compiled query
- 같은 조회를 Dapper로 작성해 비교한다(선택)
- 좋아요 카운터: 실시간 COUNT vs 비정규화 컬럼(핫 로우 경합) vs Redis
- 🚦 게이트: `pg_stat_statements` 상위 5개 쿼리 개선 표
- 🚀 운영 반영: 개선 쿼리 배포 후 운영 `pg_stat_statements`에서도 확인(운영은 데이터가 적으니 로컬과 다른 이유를 적는다)

**D10 · 부하 테스트와 커넥션 ★**
- k6 시나리오: 지도 조회 70%, 리뷰 작성 20%, 그룹 합류 10%. 목표 예시: p95 < 200ms, 에러율 < 1%
- 커넥션 풀 고갈을 일부러 재현하고(Max Pool Size 축소, 느린 쿼리) `pg_stat_activity`와 `dotnet-counters`로 진단한다
- 🚦 게이트: **incident 004**(커넥션), k6 리포트를 `docs/perf/`에 저장
- 🚀 운영 반영: k6는 로컬 대상으로만. 결론으로 정한 커넥션 풀 설정(`Max Pool Size` 등)과 EC2 인스턴스 크기·`max_connections` 관계를 운영 설정에 반영

**D11 · 캐시와 Rate Limiting (DSA #2, #3)**
- `/dsa-lab`: LRU 캐시 직접 구현 → `IMemoryCache`·Redis와 비교, 캐시 무효화 전략(리뷰 작성 시)
- `/dsa-lab`: Token Bucket 직접 구현 → ASP.NET Core `RateLimiter` 미들웨어와 비교
- k6로 캐시 적용 전후를 다시 측정한다
- 🚦 게이트: `docs/dsa/02`, `03`과 전후 수치
- 🚀 운영 반영: compose에 `redis` 서비스 추가 후 재배포(운영 중인 구성에 서비스 추가). DEP에서 넣은 기본 `RateLimiter`를 직접 구현한 Token Bucket과 비교해 교체 여부를 결정하고, 인스턴스가 2대 이상이 될 때 인메모리 한도가 깨지는 문제(→ Redis 기반)를 정리

**D12 · 배포** → **DEP 배포 주간으로 이동**(위). 여기에 남은 것은 없다. Redis 추가는 D11 운영 반영에서 한다

**D13 · 운영 검증**
- 운영 환경에 약한 부하 테스트를 돌리고 로컬과 비교한다(왜 다른가?)
- 장애 시나리오: DB 재시작 시 앱 복구, Redis 다운 시 캐시 우회(graceful degradation)

- 🚦 게이트: 장애 시나리오별 동작 기록

**D14 · 포트폴리오 정리**
- README: 아키텍처 다이어그램, ERD, 핵심 결정(ADR 링크), 트러블슈팅 요약 표(문제 → 원인 → 해결 → 수치), DSA 결과, 배포 URL

- 🚦 게이트: 처음 보는 사람이 README만 읽고 무엇을 해결했는지 3분 안에 이해할 수 있다
