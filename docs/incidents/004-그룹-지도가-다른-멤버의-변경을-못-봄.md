# 004. 그룹 지도가 다른 멤버의 북마크를 보여 주지 않다가, 리뷰를 쓰면 채운 별로 나타났다

- 날짜 / 관련 커밋: 2026-10-28 / `0bf1e24` (`feat/fe-connect`)
- 분류: 기타(클라이언트 데이터 신선도)
- 작성: Claude (사용자 요청)

## 1. 증상

- 다른 그룹원이 **북마크만** 한 장소가 내 그룹 지도에 회색 별로 보이지 않았다.
- 그 그룹원이 리뷰를 쓰고 나서야 별이 나타났는데, 회색 단계를 건너뛰고 **채운 별**로 보였다.
- 처음 보고(사용자, 그룹 "쥑쥑"): jamME 북마크 14:25 → 합류 15:10 → 리뷰 15:12(UTC). hwi는 리뷰 뒤에야 별을 봤다 → 회색 별이 **최소 47분** 보이지 않았다.
- 사용자 영향: 그룹 지도의 핵심 정보("친구가 가 보고 싶은 곳")가 화면을 다시 열기 전까지 빠진다. 오류 표시가 없어 사용자는 데이터가 없다고 믿는다.

## 2. 재현

| 항목 | 값 |
|---|---|
| 환경 | 로컬 Windows, Docker `postgres`, `dotnet run --project src/Nook.Api --launch-profile http`(:5153), `npm --prefix web run dev`(:3300) |
| 데이터 | 그룹 "쥑쥑" `01a182c5-6a9c-7983-a711-5c1c59848cbc` — hwi(방장, 슬롯 3) · dong(슬롯 0) |
| 동시성 | 브라우저 창 2개(일반 창 hwi, 시크릿 창 dong)를 나란히 띄움 |
| 절차 | ① hwi가 그룹 지도를 열어 둔다 ② dong이 새 장소를 북마크만 한다 ③ hwi 화면을 그대로 본다 |
| 재현율 | 3/3 (처음 보고 · 대조 실험 · 수정 전 확인) |

자동 테스트는 없다. `web/`에 테스트 러너가 없다(7절).

처음 보고에 나온 jamME는 그 사이 탈퇴 테스트로 지워졌다. 그래서 같은 이름의 그룹을 새로 만들어 dong으로 재현했다.

## 3. 가설과 검증

문제 공간을 **네트워크 응답**을 경계로 둘로 나눴다. 응답에 장소가 있으면 서버 쪽(DB·SQL·API·BFF·인증)은 결백하고, 화면 쪽만 남는다.

| # | 가설 | 검증 방법 | 결과 |
|---|---|---|---|
| H1 | 서버(GR-05 SQL)가 북마크만 한 장소를 뺀다 | hwi 브라우저로 BFF `GET /api/nook/groups/{id}/places`를 직접 열기 | **기각.** `"bookmarkCount":1,"soleBookmarkerSlot":0`으로 들어 있음. 통합 테스트 `Places_AggregatesPerPlace`도 이 경우를 확인함 |
| H2 | 화면이 그 별을 그리지 못한다(특히 슬롯 **0**이 JS falsy라 "단독 북마커 없음"으로 처리됨) | 데이터가 있는 상태에서 그룹을 다시 골라 그리게 함 | **기각.** 회색 별 + 슬롯 색 외곽선이 정상으로 보임 |
| H3 | 그룹 지도가 다시 불러와지지 않는다 | 대조 실험: 열어 둔 상태에서 변경 → 그대로 보기 / 다른 지도로 바꿨다 돌아오기 | **확정.** 그대로 보면 없음, 바꿨다 돌아오면 보임 |

H2의 슬롯 0 의심은 이번 재현에서 처음 생겼다. 처음 보고의 jamME는 슬롯 2였기 때문이다. 증상이 같아도 조건이 바뀌면 원인 후보가 바뀔 수 있어서 따로 기각했다.

H3 실험은 "다시 불러오기" 하나만 바꾼 대조다. "없음" 하나만으로는 약한 증거이고, "바꿨다 돌아오면 보임"과 짝을 이뤄야 **데이터는 서버에 있는데 화면이 낡았다**가 증명된다.

## 4. 근본 원인

`web/src/app/map/MapScreen.tsx`의 `reloadSaved`는 두 경우에만 호출됐다.

- `activeGroupId`가 바뀔 때(그룹을 고를 때) — `useEffect([kakaoReady, reloadSaved])`
- 내 장소 시트에서 무언가 바꿨을 때 — `onChanged={reloadSaved}`

**다른 멤버의 변경을 받아오는 경로가 없었다.** 그룹 지도는 연 순간의 스냅샷으로 남는다. 처음 보고의 경우, hwi는 jamME의 북마크와 합류 사이에 다시 불러오지 않았고 리뷰 뒤에 처음 다시 불러왔다. 그래서 회색 단계를 건너뛰고 채운 별을 봤다.

이전에 드러나지 않은 이유:
- 내 지도는 바꾸는 사람이 나뿐이고, 내 변경은 `onChanged`가 다시 불러온다.
- 원본 nook(`C:\Projects\nook\src`)에도 realtime 구독(`channel(`·`postgres_changes`)이나 복귀 시 갱신이 없다. **C#으로 옮기면서 생긴 회귀가 아니라 물려받은 설계 공백**이다.
- 백엔드 통합 테스트는 응답이 맞는지만 확인하고, 화면이 그 응답을 언제 다시 받는지는 확인 범위 밖이다.

## 5. 해결

**화면으로 돌아올 때 다시 불러온다**(A안, 사용자 결정).

```tsx
useEffect(() => {
  if (!kakaoReady) return;
  let last = 0;
  const onReturn = () => {
    if (document.visibilityState !== "visible") return;
    const now = Date.now();
    if (now - last < 1000) return;
    last = now;
    reloadSaved();
  };
  document.addEventListener("visibilitychange", onReturn);
  window.addEventListener("focus", onReturn);
  return () => { /* 두 리스너 해제 */ };
}, [kakaoReady, reloadSaved]);
```

- `visibilitychange`: 탭이나 앱 전환에서 돌아올 때. 모바일 사용 패턴이다.
- `window` `focus`: 창 두 개를 나란히 띄운 경우. 둘 다 계속 visible이라 `visibilitychange`가 나지 않는다. **이번 재현 환경이 바로 이 경우**라, `visibilitychange`만 넣었다면 수정이 안 된 것처럼 보였을 것이다.
- 탭으로 돌아오면 두 이벤트가 거의 동시에 온다. 그래서 1초 안의 두 번째 호출은 버린다.
- `reloadSaved`가 의존성에 있다. 그래서 그룹을 바꾸면 리스너가 새 `activeGroupId`를 담은 함수로 다시 등록된다(오래된 클로저 방지).

검토했지만 버린 대안:

| 안 | 버린 이유 |
|---|---|
| B. 일정 간격 폴링 | 멤버 4명 × N초마다 요청이 나가는데 대부분 변화가 없다. 늦게 도착한 이전 응답이 최신 화면을 덮는 경합이 커진다. 필요하면 DEP 이후 측정 근거를 가지고 다시 검토 |
| D. 서버 푸시(SSE/SignalR) | 백엔드에 새 인프라가 필요하고, 스케일아웃 때 연결 유지 문제가 생긴다. 2주 범위 밖 |
| E. 그대로 두고 기록만 | 보고된 증상이 그대로 남는다 |

## 7. 재발 방지

- 브라우저 수동 확인 목록에 "그룹 지도를 열어 둔 채 다른 멤버가 북마크·리뷰를 함 → 창으로 돌아오면 보임"을 추가한다.
- **남은 빈 곳**: `web/`에 테스트 러너가 없어서 이 동작을 자동으로 지키지 못한다. 이벤트 리스너 등록·중복 방지는 컴포넌트 테스트(예: Vitest + Testing Library)로 확인할 수 있다. 도입 여부는 DEP 때 CI와 함께 결정한다.
- 아직 확인하지 않은 것:
  - 1초 중복 방지를 빼면 요청이 2건이 되는지(변이 확인)
  - `reloadSaved`에 취소 장치가 없어서, 그룹을 빠르게 바꿀 때 이전 응답이 늦게 도착해 덮어쓰는 경합

## 8. 배운 것

- 응답 경계에서 시스템을 반으로 자르면, 한 번의 관찰로 서버 쪽 원인 후보를 한꺼번에 지울 수 있다.
- 증상이 같아도 재현 조건이 바뀌면(슬롯 2 → 0) 새 원인 후보가 생긴다. 그 후보도 따로 기각해야 한다.
- "언제 다시 불러오는가"는 서버를 빠르게 해도 줄지 않는 지연이다. 화면 데이터에도 신선도 정책이 설계 항목으로 필요하다.
