## 대화에서 나온 판단

### 포트폴리오·베타
- 포트폴리오 가치는 기능이 아니라 이야기: "원본의 결함(부분 커밋, TOCTOU, 고아 그룹, 정원 초과)을 재현 → 원인 → 해결 → 측정으로 증명". 근거 자료는 ADR·ERD·원본 비교(이미 있음) + incident·측정값(예정)
- 베타 서비스는 D14 이후 별개 일: 인증·인가(AU-01 미정), 이미지 업로드 검증, rate limit, Storage 권한, 개인정보 처리방침(이메일·위치), 백업·모니터링
- 베타는 **데모 계정 + 시드 데이터**로 시작 권장 (공개 가입은 개인정보 의무가 생김)
- 완성 전에 지원해도 됨: README에 "진행 중" + 로드맵

### 시간 차등 원칙 (일정과 무관하게 지금부터 적용 가능)
D3-1 원칙 "결정을 미룰지는 되돌리는 비용으로"를 시간 배분에도 적용한다.

| 되돌리는 비용 | 예 | 쓸 시간 |
|---|---|---|
| 비쌈 (데이터 형태, 공개 계약) | PK·FK, 컬럼 의미, API 경로, 인증 방식 | 깊게 |
| 쌈 (설정값, 인덱스, 내부 구현) | 고아 이미지 N, 인덱스 추가, 배치 주기 | 15분 제한 → 기본값 + "예상" 기록, 측정 때 재검토 |

- 일정 재산정 시점: **D5 종료 후** (실행 비중이 큰 D4·D5의 실측 속도로)

## 순서를 바꾸면 학습이 사라지나 (질문 4 답)

결론: 거의 사라지지 않는다. 순서에 묶인 것은 **D13 하나**이고, D13을 맨 끝에 두면 끊어지는 의존이 없다.

| 연결 | 바꾼 순서에서 | 손실 |
|---|---|---|
| D12 compose의 `redis` (D9·D11 도입) | 첫 배포는 api + postgres + caddy. D11에서 Redis 추가 후 재배포 | 없음 — 운영 중 구성에 서비스 추가 연습 |
| D13 운영 부하 테스트 vs 로컬 (D10 k6 필요) | D13은 원래 자리(D11 뒤) 유지 | 없음 |
| D13 Redis 다운 시 우회 (D11 필요) | 위와 같음 | 없음 |
| D8 인덱스 튜닝 | 이미 배포된 DB에 반영 | **늘어남** (아래) |
| D11 Rate Limiting | D12에 기본 `RateLimiter` 최소 적용, D11에서 Token Bucket 직접 구현·비교는 그대로 | 없음 |
| D7 DSA, D9 ORM | 로컬 작업, 배포와 무관 | 없음 |

오히려 배우는 것 (운영 중인 시스템을 계속 바꾸는 경험)
- D8 인덱스를 데이터가 있는 DB에 `CREATE INDEX CONCURRENTLY`로 반영 — 트랜잭션 안에서 못 돌아서 EF 마이그레이션과 부딪히는 지점을 직접 겪음. ERD의 "인덱스는 나중에 CONCURRENTLY로 싸게 추가" 주장도 검증
- ADR-003(마이그레이션 적용 전략)이 실제 문제가 됨 — Day마다 운영 DB에 적용
- 환경 분리 — D8의 1,000만 행 시드는 운영 DB에 넣으면 안 됨

진짜 위험: **의존이 아니라 동기.** 데모가 완성되고 지원을 시작하면 D7~D11 동기가 떨어질 수 있다. "대용량" 학습 목표는 대부분 D8·D10에 있다.
- 장치 1: `개발_프로세스.md` "버리지 않는다"에 D8·D10 유지 + 바뀐 순서 명시
- 장치 2: 배포 이후 Day마다 게이트에 "운영 반영" 추가(D8 인덱스 마이그레이션, D11 Redis 등) → 이후 작업도 포트폴리오 URL에 쌓임
- 면접 관점: "인덱스를 튜닝했다"보다 "운영 중인 DB에 무중단으로 인덱스를 추가했다"가 이야기할 거리가 많다
