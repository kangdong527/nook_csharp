# ADR-010 그룹 동시 합류: 그룹 행 비관적 잠금(FOR UPDATE)

- 상태: 채택됨
- 날짜: 2026-10-25
- 결정자: 강동진
- 작성: Claude (사용자 요청, 결정은 D6-1 세션)

## 맥락

정원 4명(R-GR-01)은 `group_members` 여러 행에 걸친 규칙이라 DB CHECK로 표현할 수 없다(erd.md group_members).
`Group.AddMember`의 정원 검사는 요청마다 따로 있는 메모리 복사본을 보므로 동시 요청을 막지 못한다.
5명 동시 합류 테스트로 재현하니 빈자리 3인 그룹이 6명이 됐다(incident 003). 원본 nook의 "정원 초과" 결함과 같다.

R-GR-03은 "먼저 처리된 요청이 최종 멤버가 되고, 나머지는 정원 초과로 거절"을 요구한다. 즉 결과가 **선착순**이어야 하고, 빈자리가 있는데 거절되면 안 된다.

## 결정

**합류 트랜잭션은 인원을 읽기 전에 그룹 행을 `SELECT … FOR UPDATE`로 잠근다.** 격리 수준은 기본값(READ COMMITTED)을 유지한다.

1. 잠그는 문장과 멤버를 읽는 문장을 **나눈다**. 한 문장(JOIN)으로 합치면 대기 뒤에도 멤버를 대기 전 스냅샷으로 읽는다(incident 003 실험 1).
2. 초대 코드로 찾기와 잠그기는 한 문장이다(`LockByInviteCodeAsync`, erd.md groups Q1·Q2). 잠그기 전에 그룹을 따로 읽지 않는다. 같은 DbContext의 식별 맵이 옛 인스턴스를 돌려줄 수 있기 때문이다.
3. 정원·중복 판단은 `Group.AddMember`에 남긴다. 잠금은 판단 재료(멤버)를 최신으로 만들 뿐이다.
4. 트랜잭션 경계는 핸들러가 쥔다(D5-3). DB가 필요 없는 검사(초대 코드 형식)는 트랜잭션 밖, 앞에서 끝낸다.
5. 스키마는 바꾸지 않는다. erd.md의 "인원 수 컬럼은 두지 않는다"를 유지한다.

## 검토한 대안

| | (가) `FOR UPDATE` ✅ | (나) 카운터 컬럼 + 조건부 UPDATE | (다) SERIALIZABLE + 재시도 |
|---|---|---|---|
| 어디서 기다리나 | DB 행 잠금 대기 | DB 행 갱신 대기 → WHERE 재평가 → 0행 | 기다리지 않음. 충돌 시 40001 → 앱이 재시도 |
| 스키마 변경 | 없음 | `member_count` + CHECK + backfill | 없음 |
| 추가 코드 | 리포지토리 메서드 1개 + 핸들러 트랜잭션 | 멤버 수가 바뀌는 경로 5곳에서 카운터 동기화 | 재시도 루프, 40001 처리 |
| 재시도 없을 때 결과 | 3 성공 / 2 `GroupFull` | 3 성공 / 2 `GroupFull` | **1 성공 / 4 직렬화 실패**(빈자리가 있는데 거절) |
| 같은 도구로 풀리는 다른 문제 | 탈퇴 Write Skew(R-GR-09), 회원당 그룹 수(R-GR-04, users 행) | R-GR-04는 다른 방법이 필요 | 모든 경로에 재시도 필요 |
| 얻는 것 | 단순함, 선착순 보장 | `CHECK (member_count <= 4)`로 DB가 정원을 직접 보장, 목록에서 COUNT 불필요 | 잠금 순서·데드락을 신경 쓰지 않아도 됨 |
| 잃는 것 | 대기 중 연결 점유, 잠금 순서를 지키지 않으면 데드락 | 비정규화(쓰기 두 곳, 불일치 위험), erd.md 결정 뒤집기 | 버려지는 작업, 같은 인덱스 페이지의 다른 그룹과 가짜 충돌 |

- **(나)를 버린 이유**: 처음에는 (나)를 골랐다. 근거는 "추후 그룹 목록에 멤버 수 표시" + "코드 복잡도"였다. 그런데 확인해 보니 그룹 목록·검색 유스케이스는 `usecases.md`에 없고(GR-01~05), 합류 경로의 세기는 최대 4행을 PK 앞 열로 읽는다(추론, 미측정). 동시성 해결에는 카운터가 필요 없으므로, 목록 요구가 생기면 그때 D9 카운터 전략에서 COUNT와 카운터를 **측정해** 비교한다.
- **(다)를 버린 이유**: 재시도 없이는 R-GR-03(빈자리가 있으면 받아야 함)을 어긴다. 경합이 같은 행에 집중되는 선착순 문제라 낙관적 방식의 장점(경합이 드물 때 대기 없음)이 살지 않는다.
- 단순 대안 둘도 기각했다. 트랜잭션만 열기는 공통 행을 잠그지 않아 대기가 없다. 조건부 INSERT(`… WHERE (SELECT count(*) …) < 4`)는 서로 다른 행을 INSERT해 경합할 한 행이 없다.

## 결과

- 동시 합류 테스트: 6명 → 4명(성공 3 · `GroupFull` 2), 5/5 반복. `FOR UPDATE` 제거 변이 3/3 빨간불(incident 003).
- 리뷰 동시 수정(ADR-009, incident 002)은 **낙관적** 버전 토큰을 골랐고, 합류는 **비관적** 잠금을 골랐다. 기준은 같다: 경합이 드물고 재시도가 싸면 낙관적, 같은 행에 경합이 집중되고 결과가 선착순이어야 하면 비관적.
- 이 결정이 만든 숙제
  - ~~**잠금 순서**~~ → 후속 결정 1·2로 해결
  - ~~탈퇴(R-GR-09)도 같은 잠금을 쓴다~~ → 후속 결정 3으로 해결(`LockByIdAsync`)
  - 잠금 대기로 늘어나는 지연은 측정하지 않았다 → D10 k6(같은 그룹 동시 합류 p95)
  - 트랜잭션 안에 외부 I/O를 넣으면 그 시간이 대기열 전체의 지연이 된다(CLAUDE.md 규칙의 동시성 측면)

## 후속 결정 (2026-10-25 D6-1, 2026-10-26 반영)

R-GR-02/04(회원당 참여 그룹 3개)와 R-GR-09(마지막 멤버 탈퇴 시 그룹 삭제)를 구현하면서 정했다.

| # | 결정 | 근거 | 검증 |
|---|---|---|---|
| 1 | **잠금 순서는 항상 users → groups** | 같은 회원의 합류·생성이 서로 다른 그룹이면 그룹 행 잠금으로는 한 줄로 못 세운다. 공통 행은 users 행이다(사용자 답). 행 두 개를 잠그는 경로는 순서를 하나로 고정해야 순환 대기가 없다 | 참여 2개 회원의 합류 2 + 생성 1 동시 → 4개였던 것이 5/5 성공 1·실패 2·3개. 반대 순서 학습 테스트에서 40P01(약 1초) 재현 |
| 2 | **users 잠금 강도는 `FOR NO KEY UPDATE`** | users 행을 FK로 참조하는 INSERT(`group_members`)는 FK 검사로 `FOR KEY SHARE`를 잡는다. `FOR UPDATE`는 이것과 충돌하고, `FOR NO KEY UPDATE`는 통과시키면서 자기끼리는 충돌한다 | 강도 변이(`FOR UPDATE`) → FK INSERT 시간 초과 |
| 3 | **탈퇴는 groups 행만 잠근다** | 탈퇴는 참여 수를 줄이기만 해서 R-GR-02를 깰 수 없다(사용자 판단). 남은 두 멤버의 동시 탈퇴(Write Skew, 빈 그룹)는 그룹 행 하나로 막힌다. 잠그는 행이 하나라 순서 문제가 없다 | 마지막 두 멤버 동시 탈퇴 10라운드 × 3회 그룹 0개, 잠금 제거 변이 10/10 빈 그룹 |
| 4 | 생성은 users 행만 잠근다 | 새 그룹이라 잠글 groups 행이 없다. 결정 1의 순서와 부딪히지 않는다 | — |

- 같은 잠금을 쓰는 경로끼리만 줄을 선다. 합류의 users 잠금을 빼면 생성 쪽 잠금만으로는 못 막았다(변이 → 5개).
- 이 순서를 지키는 경로를 추가할 때는 핸들러 주석(`JoinGroupHandler`·`CreateGroupHandler`·`LeaveGroupHandler`)에 잠그는 행을 적는다. 반대 순서 경로가 하나라도 생기면 교착이 다시 열린다.
