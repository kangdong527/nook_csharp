# ADR-005 외래 키 유지

- 상태: 채택됨
- 날짜: 2026-10-11
- 결정자: 강동진
- 작성: Claude (사용자 요청, 결정 내용은 D2-3 세션의 사용자 결정)

## 맥락

애그리거트 경계를 정하면서 "경계 밖은 ID로만 참조한다"(예: `Review`는 `PlaceId`만 든다)를 결정했다.
이때 DB에서도 외래 키(FK)를 걸지 말아야 하는지, 또는 대리 키를 없애고 복합 키를 쓰면 FK를 쓸 수 없는지가 질문으로 나왔다.
처음 판단은 "나중에 FK가 문제가 되면 제거하기 어려우니 처음부터 걸지 않는다"였다.

## 결정

- **FK를 유지한다.** 애그리거트 사이 참조가 Domain에서 ID뿐이어도, DB는 FK로 존재하지 않는 대상을 가리키는 행(고아 행)을 저장 시점에 거부한다
- 근거: 비용의 방향이 처음 판단과 반대다
  - FK **제거**(`DROP CONSTRAINT`)는 카탈로그만 바꾸는 메타데이터 변경이라 싸다
  - FK를 **나중에 추가**하면 기존 행 전체를 검증해야 하고, 그동안 잘못 들어간 행이 있으면 추가 자체가 실패한다
  - 그러니 처음에 걸고, 필요해지면 끄는 쪽이 되돌리기 쉽다
- 대리 키의 수와 FK 사용은 무관하다. 복합 PK(예: Bookmark의 `(user_id, place_id)`)여도 각 열에 FK를 건다

## 고려한 대안

- **FK 없이 애플리케이션이 참조 무결성을 보장**: 쓰기 경로가 하나뿐일 때는 동작하지만, 탈퇴·삭제처럼 여러 테이블에 걸친 작업에서 부분 커밋이나 경합이 생기면 고아 행이 조용히 쌓인다(원본 nook의 부분 커밋 결함과 같은 종류) → 기각

## 결과

- D3 스키마의 모든 참조 열에 FK를 건다. `ON DELETE` 동작(CASCADE / RESTRICT)은 탈퇴(PF-02)·리뷰 삭제 유스케이스에 맞춰 D3에서 열마다 정한다
- 관련 결정(D3 확정 예정): Bookmark·Like·GroupMember는 대리 키 없이 복합 PK. 유일성 규칙(R-BM-01·R-LK-01·R-GR-07)이 PK 자체가 되어 인덱스가 하나로 줄어든다. ReviewImage는 순서·교체 때문에 식별자를 유지한다
- 대용량 삭제·적재(D8) 때 FK 검사 비용을 측정하고, 문제가 되면 그때 근거와 함께 이 ADR을 갱신한다
