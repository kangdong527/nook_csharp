# ADR-011 리뷰 수정 버전을 화면까지 왕복: 바디 필드 `version`, 불일치는 409

- 상태: 채택됨
- 날짜: 2026-10-26
- 결정자: 강동진
- 작성: Claude (사용자 요청, 결정은 D6-2 세션)

## 맥락

incident 002에서 리뷰 동시 수정을 `FOR UPDATE` + 낙관적 동시성 토큰 `reviews.version`으로 막았다.
그러나 이 토큰은 **한 요청 안**(조회 → 저장)만 지킨다. 핸들러는 저장 직전에 리뷰를 새로 읽으므로, 비교 기준이 "방금 읽은 최신 값"이다.

```
10:00  화면 A 열기            목록 조회 → 본문·이미지
10:02  기기 B 수정 커밋       reviews.version 3 → 4
10:05  화면 A "저장"          PUT (버전 없음)
         조회               → version 4를 읽음
         저장               → UPDATE … WHERE version = 4 → 1행, 성공  ← 기기 B의 수정을 덮어씀
```

요청 안에는 낡은 데이터가 없다. 낡은 것은 **사람이 본 화면**이다. 사람이 무엇을 보고 결정했는지를 서버가 알려면 토큰이 화면까지 갔다가 돌아와야 한다.

## 결정

| # | 질문 | 결정 |
|---|---|---|
| A | 토큰 | 기존 `reviews.version` 컬럼을 그대로 쓴다(`xmin` 아님) |
| B | 전달 방식 | 바디 필드. 응답 `ReviewView`·`PlaceReviewView`에 `version`, RV-02 multipart 폼에 `Version` |
| C | 불일치 응답 | `409` `Review.EditConflict`(RV-02 6c와 같은 에러) |
| D | 누락 | 필수. 빠지면 `400`(모델 검증) |

1. **불투명 값 계약.** 클라이언트는 `version`을 해석하지 않는다(+1, 크기 비교 금지). 받은 값을 그대로 돌려보낸다. 이 계약이 A의 변경 비용을 서버 안으로 가둔다.
2. **비교 위치는 핸들러, 권한 검사(4b) 뒤·업로드(5) 앞.**
   - 업로드 앞: 낡은 화면을 이미지 업로드 전에 거절해 고아를 만들지 않는다.
   - 권한 뒤: 남의 리뷰에 409를 주면 "그사이 수정됐다"는 사실이 새어 나간다.
   - 도메인(`Review.Edit`)이 아니라 핸들러: "화면이 무엇을 봤는가"는 HTTP 왕복에서 생기는 유스케이스의 관심사다. 애그리거트는 이미 "성공하면 Version + 1"로 자기 버전을 관리한다.
3. **2단 판정.** 사전 비교를 통과하면 읽은 버전 = 화면의 버전이다. 그래서 사전 비교와 저장 사이의 경합은 기존 `UPDATE … WHERE version = <읽은 값>`이 그대로 최종 판정한다. 별도 장치가 필요 없다. 구조는 RV-01의 "사전 확인 + UNIQUE 최종 판정"과 같다.
4. 요청 바인딩은 `int?` + `[Required]`다. `int`면 누락이 0으로 바인딩되고, 시드 직후 리뷰의 버전도 0이라 "안 보냄"과 "버전 0을 봄"을 구분할 수 없다(`CreateReviewRequest.PlaceId`와 같은 이유).

## 검토한 대안

| | 채택 | 대안 | 대안을 버린 이유 |
|---|---|---|---|
| A 토큰 | `reviews.version` | PostgreSQL `xmin` | 마이그레이션이 필요 없지만 본문과 상관없는 변경(VACUUM FREEZE, 덤프·복원, 앞으로 넣을 수 있는 비정규화 컬럼 갱신)에도 값이 바뀌어 **거짓 충돌**을 만든다. 32비트라 순환한다. `version`은 이미 있고 무엇이 올리는지 코드가 통제한다 |
| B 전달 | 바디 필드 | `ETag` / `If-Match` 헤더 | ETag는 응답 하나에 하나다. 단건 `GET /reviews/{id}`가 없고 화면은 장소별 목록(PL-02)에서 편집으로 들어가므로 항목별 버전을 담을 수 없다 |
| C 응답 | 409 재사용 | 412 Precondition Failed | 412는 `If-Match`를 쓸 때의 표준이다. 바디 필드라면 409가 자연스럽고 FE의 분기가 하나 준다 |
| D 누락 | 필수 | 선택(없으면 지금처럼) | 선택이면 화면 사이의 Lost Update가 다시 열린다. FE가 아직 없어 지금 필수로 해도 깨지는 클라이언트가 없다 |

## 결과

- 테스트: `Edit_WithVersionSeenBeforeOtherEdit_Returns409AndUploadsNothing`(목록에서 받은 버전 → 다른 수정 커밋 → 409, 스토리지 개수 그대로), `Edit_WithoutVersion_Returns400AndUploadsNothing`. 사전 비교가 없을 때 앞 테스트가 200으로 실패하는 것을 확인했다.
- 나중에 바꾼다면
  - **A → `xmin`**: 서버 내부(매핑 교체, `Review.Version` 제거, 컬럼·CHECK 삭제 마이그레이션). 클라이언트는 그대로(불투명 값 계약). 배포 순간 열려 있던 화면은 한 번 409를 받는다.
  - **B → ETag**: 계약 변경. 단건 GET을 새로 만들고 FE 편집 흐름도 바꿔야 한다. D가 필수이므로 과도기에는 폼 필드와 `If-Match`를 둘 다 받아야 한다. 클라이언트가 우리 FE 하나라 같은 배포 주기에 맞출 수 있다.
