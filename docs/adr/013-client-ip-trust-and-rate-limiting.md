# ADR-013 클라이언트 IP 신뢰 고리와 요청 제한 위치

- 상태: 채택됨
- 날짜: 2026-11-09
- 결정자: 강동진
- 작성: Claude (사용자 요청, DEP 7단계 세션)
- 관련: dep-plan 7단계·§4, ADR-003(컨테이너 배치·네트워크), PR #34

## 맥락

공개 전(dep-plan 결정 6) 요청 제한이 필요하다. 이메일당 제한(`MagicLinkPolicy`, 15분 3회)은 이미 있지만 **한 IP가 주소를 바꿔 가며** 매직 링크를 요청하는 경우(메일 폭탄, SES 비용)는 막지 못한다. 그래서 IP 기준 제한이 필요하다.

문제는 IP다. 요청은 **Caddy → web(Next BFF) → api 2단 프록시**를 거친다(ADR-003 — 바깥에 열린 건 Caddy뿐이고 api는 Caddy에 경로가 없다). api가 보는 TCP 상대는 언제나 web 컨테이너라, 그대로 세면 전원을 한 명으로 본다. 반대로 `X-Forwarded-For`(XFF)를 무조건 믿으면 클라이언트가 값을 적어 칸을 바꿔 가며 제한을 우회한다. dep-plan §4는 프록시를 1단(Caddy)으로 가정했는데 실제는 2단이었다.

## 결정

| # | 질문 | 결정 |
|---|---|---|
| 1 | 어디서 제한하나 | **C# API** (.NET `RateLimiter`). 이메일 제한이 이미 api에 있어 방어가 한 곳에 모이고, 업무 맥락(경로·인증)을 안다 |
| 2 | 클라이언트 IP를 어떻게 믿나 | 고리 3개가 모두 성립해야 한다. ① **Caddy**: `trusted_proxies`를 두지 않는다 → 들어온 XFF를 버리고 실제 접속 IP로 덮어쓴다 ② **BFF** `apiFetch`: 받은 XFF의 **맨 오른쪽 값만**(= Caddy가 적은 값) api로 넘긴다. web 포트는 바깥에 열려 있지 않아 Caddy만 web에 닿는다 ③ **api**: `ForwardedHeaders`가 `KnownNetworks`(backend 서브넷)에서 온 XFF만 믿고 `ForwardLimit = 1` |
| 3 | 신뢰 대역 | compose `backend` 서브넷을 **`10.89.0.0/24`로 고정**하고 `ForwardedHeaders:KnownNetworks`에 같은 값. Docker 기본 풀(172.17~31·192.168)과 AWS 기본 VPC(172.31/16, DNS 172.31.0.2)와 겹치지 않게 골랐다 |
| 4 | 설정이 없으면 | 개발 밖에서는 **시작 실패**(fail-fast, ADR-003 결정 1과 같은 방식). 목록이 비면 **미들웨어를 켜지 않는다** — `ForwardedHeadersOptions`는 신뢰 목록이 비면 "모두 믿음"으로 동작한다(변이로 실측) |
| 5 | 무엇을 믿나 | `X-Forwarded-For`만. `Proto`·`Host`는 쓰지 않는다 — api는 내부 HTTP만 받고 TLS는 Caddy에서 끝난다 |
| 6 | 범위·수치(시작값) | 전체: IP당 **300/분**(지도 이미지 GET, CGNAT·공유 IP 고려). 매직 링크 요청·소비: 각각 IP당 **5/10분**. 거절 로그를 보고 조정한다. 설정 `RateLimit:*` |
| 7 | 칸 나누기 | 인증 한도는 **IP + 경로**. 요청(메일 비용)과 소비(토큰 대입)는 막는 대상이 다르고, 하나로 세면 가입 1회(요청 1 + 소비 2)가 5칸 중 3칸을 쓴다 |
| 8 | 창·대기열 | 고정 창, `QueueLimit = 0`(대기열은 공격자에게 서버 자원을 쥐여 준다) |
| 9 | 거절 응답 | 429 + `Retry-After` + ProblemDetails `title = RateLimit.Exceeded`(다른 오류와 같은 계약). 로그는 IP·메서드·경로만 — 본문의 이메일은 남기지 않는다(개인정보) |
| 10 | 제외 | `/health/live`·`/health/ready`(`DisableRateLimiting` — 전체 한도도 제외). 배포 스크립트의 반복 확인이 한도를 먹지 않게 |

## 기각한 안

| 안 | 기각 이유 |
|---|---|
| Next BFF에서 제한 | api가 IP를 몰라도 되지만 제한기를 TS로 새로 만들어야 하고, api 로그에는 여전히 web IP만 남는다. 이메일 제한(api)과 방어가 두 곳으로 갈린다 |
| Caddy에서 제한 | 가장 앞에서 막지만 공식 이미지에 없는 `caddy-ratelimit` 플러그인으로 커스텀 빌드가 필요하다(이미지·Trivy 관리 대상 증가). 앱 로그에 실제 IP가 없다 |
| XFF 맨 왼쪽 값 사용 | 맨 왼쪽은 클라이언트가 적은 값이라 누구나 바꿀 수 있다 |
| `KnownProxies`에 web 컨테이너 IP 지정 | 컨테이너를 다시 만들면 IP가 바뀐다. 서브넷 고정이 안정적이다 |
| 사설 대역 전체(10/8·172.16/12·192.168/16) 신뢰 | 같은 호스트의 다른 컨테이너나 VPC 안의 다른 장비가 XFF를 위조할 여지가 생긴다 |

## 결과

- 확인(테스트): `RateLimitApiTests` 5개 — 6번째 429·`Retry-After`·메일 미발송, 신뢰 프록시 뒤 클라이언트별 칸, 신뢰 밖 XFF 무시, 요청·소비 칸 분리, 전체 한도. 변이 4개(`UseForwardedHeaders` 제거, 신뢰 목록 비움, 칸에서 경로 제거, `[EnableRateLimiting]` 제거)가 각각 빨간불
- 확인(실측, 로컬 compose): 매번 다른 XFF를 위조한 매직 링크 6회 → 6번째 429, api 로그에 실제 접속 IP(`172.22.0.1`)
- 서브넷을 바꾼 뒤 기존 스택은 `down` 후 `up` — 이어 붙이면 `db` DNS 별칭이 빠진다(dep-plan §4)
- 저장소가 프로세스 메모리라 **인스턴스가 하나일 때만** 맞다. 늘리면 분산 저장소(Redis 등)가 필요하다. 재시작하면 창이 초기화된다
- IPv6를 열면 주소 하나가 아니라 /64 단위로 묶어야 한다(한 회원이 주소를 많이 가진다)
- 남은 것: BFF `/api/auth/*`가 `Retry-After`를 화면으로 넘기지 않고 429 문구도 없다(FE)
- 이 고리 중 하나를 바꿀 때(Caddy `trusted_proxies` 추가, CDN·로드 밸런서를 앞에 둠, BFF 전달 방식 변경, 서브넷 변경)는 **이 ADR을 다시 연다**. 고리가 하나라도 빠지면 위조 XFF로 제한을 우회할 수 있다
