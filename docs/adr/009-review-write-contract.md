# ADR-009 리뷰 쓰기 규약: 이미지 정리는 배치, 삭제는 멱등 + 403

- 상태: 채택됨
- 날짜: 2026-10-23
- 결정자: 강동진
- 작성: Claude (사용자 요청, 결정은 D5-7 세션 RV-01~03 상세화)

## 맥락

RV-01(작성)·RV-02(수정)·RV-03(삭제)는 모두 **DB와 이미지 스토리지를 함께** 바꾼다.
CLAUDE.md 규칙상 업로드(외부 I/O)는 트랜잭션 밖, 그것도 앞에 둔다. 그래서 "스토리지는 바뀌었는데 DB는 롤백"되는 경우가 반드시 생긴다.
원본 nook은 이 자리에서 부분 커밋(이미지 유실·고아)을 냈다.

삭제 응답도 정해야 했다. 더블클릭·네트워크 재시도·남의 리뷰를 각각 어떻게 응답할지, 동시 요청에서도 같은 답이 나오는지가 문제였다.

## 결정

### 1. 이미지 정리는 주기 배치만 한다 (RV-01·02·03 공통)

- **DB가 진실의 원천**이다. 스토리지는 DB를 따라간다
- 실패 즉시 삭제, 커밋 후 즉시 삭제 모두 **하지 않는다**
- 배치는 "DB가 참조하지 않고, 올라간 지 N이 지난 객체"를 지운다
  - 유예 기간 N: 업로드~커밋 사이의 이미지를 고아로 오판하지 않게. 요청 타임아웃보다 충분히 크게(예: 하루)
- 결과적으로 남을 수 있는 것은 **고아 파일(비용)**뿐이고, **깨진 참조(회원이 보는 오류)**는 생기지 않는다
- D5는 스토리지 인터페이스 + 가짜 구현. 실제 스토리지(S3)와 배치는 DEP 주간

### 2. RV-01 작성 응답: `201 Created`

- `Location: /reviews/{id}`, 본문은 생성된 리뷰 + `star`(항상 `fill`)
- BM·LK는 관계 행 토글이라 `200`. 리뷰는 id를 가진 새 자원이라 성격이 다르다

### 3. RV-03 삭제: 한 문장 DELETE + 영향 행 수로 판정 (C안)

```
DELETE FROM reviews WHERE id = @id AND user_id = @me RETURNING place_id
```

| 영향 행 | 재조회 | 응답 |
|---|---|---|
| 1 | 안 함 | `200 { changed: true, star }` (`place_id`로 별 계산) |
| 0 | 리뷰 없음 | `200 { changed: false, star: null }` — 멱등 |
| 0 | 리뷰 있음 | `403` — 남의 리뷰 |

- 판정은 **DELETE의 영향 행 수**로 한다. 재조회는 "왜 0행인가"를 가리는 데만 쓴다
- 동시 삭제 두 번: 둘째 DELETE는 첫째의 행 잠금을 기다린 뒤 0행 → 성공(`changed=false`)
- 재조회와 삭제 사이의 틈은 "아무것도 안 지웠는데 성공"으로만 잘못 분류될 수 있어 무해하다
- `star=null`: 지워진 행에서는 장소를 알 수 없다. 프론트는 `changed=false`면 별을 갱신하지 않는다

### 4. 남의 리뷰는 `403` (RV-02·RV-03 공통)

- 리뷰는 장소 상세(PL-02)에서 원래 공개되는 정보다. 존재를 숨길 이유가 없다
- 그래서 의미가 정확한 403을 쓴다

## 고려한 대안

- **커밋 후 즉시 스토리지 삭제**: 고아가 덜 남는다. 그러나 삭제 실패 처리가 또 필요하고, 결국 배치가 있어야 한다. 경로가 둘이 된다 → 기각
- **커밋 전 스토리지 삭제(RV-02의 빠진 이미지)**: 롤백되면 DB는 그 키를 계속 참조하는데 파일은 없다 → 깨진 참조. 기각
- **삭제 A안 — 없음·남의 것 모두 `200 changed=false`**: 완전 멱등 + 존재 숨김. 그러나 남의 리뷰 삭제 시도가 성공처럼 보이고, 프론트의 잘못된 ID 전송 버그가 조용히 묻힌다 → 기각
- **삭제 B안 — 없음·남의 것 모두 `404`**: 숨김은 지키지만 재시도가 404를 받는다. 프론트가 "DELETE의 404는 성공"이라는 특별 규칙을 알아야 한다 → 기각
- **확인 후 삭제(SELECT → DELETE)**: 동시 요청에서 둘 다 "있음, 내 것"을 보고 둘째 DELETE가 0행이 된다. 판정이 사전 확인에 기대면 TOCTOU → 기각
- **삭제 요청에 `place_id`를 받아 언제나 `star` 계산**: 클라이언트 값을 믿어야 하고 URL이 어색하다 → 기각(`null` 채택)

## 결과

- 고아 파일은 배치가 돌기 전까지(최소 유예 기간 N) 스토리지에 남는다. 비용으로 받아들인다
- 403 응답으로 리뷰 ID의 존재 여부가 드러난다. 공개 정보라 받아들인다
- `star`가 `null`일 수 있어 응답 형태가 경우에 따라 다르다. 프론트(FE 단계)는 `changed`를 먼저 본다
- 오늘 쓴 리뷰를 지우면 오늘 다시 쓸 수 있다(UNIQUE가 남은 행만 본다). 원본 PM과 확인 전이라 **미결**로 둔다 — `usecases.md` RV-03
- LK-01(좋아요 취소 멱등)·incident 001(사전 확인 대신 쓰기 결과로 판정)과 같은 원칙이다
