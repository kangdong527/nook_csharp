# incident-log — 측정 가능한 트러블슈팅 기록

포트폴리오에서 설득력이 있는 것은 "~를 적용했다"가 아니라 **"이 현상을 이렇게 재현했고, 원인은 이것이었으며, 수치가 이렇게 바뀌었다"**이다.
기록은 사용자가 쓴다. Claude는 아래 템플릿을 채울 재료(로그, 측정 명령)를 함께 찾고, 빈 칸이나 근거가 없는 주장을 지적한다.

## 규칙

- 파일: `docs/incidents/NNN-짧은-제목.md` (NNN은 001부터)
- **Before/After 수치가 없으면 완료가 아니다.** 측정 도구: `EXPLAIN (ANALYZE, BUFFERS)`, k6(p95, RPS, 에러율), BenchmarkDotNet, `dotnet-counters`, `pg_stat_statements`, `pg_stat_activity`
- 재현 스크립트나 테스트를 리포에 남긴다(경합 재현 테스트, k6 스크립트, 시드 스크립트)
- "왜 다른 해결책이 아닌가"를 최소 1개 쓴다

## 템플릿

```markdown
# NNN. <한 줄 제목 — 증상이 드러나게>

- 날짜 / 관련 커밋·PR:
- 분류: 동시성 | 쿼리 성능 | 커넥션 | 메모리 | 배포 | 기타

## 1. 증상
무엇이 어떻게 잘못 보였나. 사용자 관점 영향.

## 2. 재현
환경(데이터 건수, 동시 사용자 수), 재현 명령/테스트 이름, 재현율.

## 3. 가설과 검증
| 가설 | 검증 방법 | 결과 |
|---|---|---|

## 4. 근본 원인
코드/쿼리/설정 수준에서. 왜 이전엔 드러나지 않았나.

## 5. 해결
선택한 방법과 코드 위치. 검토했지만 버린 대안과 이유.

## 6. 결과 (Before → After)
| 지표 | Before | After |
|---|---|---|

## 7. 재발 방지
추가한 테스트·제약조건·알림·체크리스트.

## 8. 배운 것
2~3줄.
```

## 이 프로젝트에서 나올 법한 사건 (원본 nook의 결함에서 출발)

- 그룹 동시 합류 → 정원 4명 초과 (TOCTOU) → 비관적 락 / 조건부 UPDATE / Serializable+재시도 비교
- 그룹 생성 중 실패 → 고아 그룹 (부분 커밋) → 트랜잭션 경계 재설계
- 리뷰+이미지 저장 중 업로드 실패 → 이미지 유실 → 업로드 → URL 확보 → 단일 트랜잭션
- 피드 OFFSET 깊은 페이지 지연 → Keyset 페이지네이션
- 지도 bbox 쿼리 Seq Scan → 인덱스 설계
- 부하 테스트 중 `connection pool exhausted` → 풀 크기, 커넥션 수명, async 누수 점검
- 리뷰 목록 N+1 → `Include`/projection/split query
- 좋아요 카운터 핫 로우 경합 → 비정규화 전략 비교
