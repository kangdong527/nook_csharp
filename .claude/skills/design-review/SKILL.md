## 체크리스트

### A. 클래스·엔티티
- 불변식이 **생성자/팩토리 메서드**에서 강제되는가? (리뷰 10~50자, 이미지 ≤3, 닉네임 2~12자, 그룹 정원 4)
- public setter로 불변식을 우회할 수 있는가? 컬렉션을 `List<T>`로 노출해 밖에서 `Add` 할 수 있는가?
- 값 객체로 뺄 후보: 좌표(Lat/Lng), 초대코드, 닉네임, 리뷰 본문
- 애그리거트 경계: 함께 바뀌어야 하는 것만 묶었는가? (Group↔GroupMember, Review↔ReviewImage)
- 별 상태(empty/gray/fill)는 저장할 값인가, 계산할 값인가?
- nullable 참조 타입(`?`)이 실제 도메인의 "없을 수 있음"과 일치하는가?
- 시간: `DateTime` 대신 `DateTimeOffset`/UTC, 테스트할 수 있게 `TimeProvider`를 쓰는가?
- 실패 처리: 예상 가능한 실패(정원 초과, 중복 합류)는 Result, 예상 불가능한 실패는 예외 — 원본 nook과 같은 원칙인가?

### B. DB 스키마
- PK 타입 선택 근거(bigint identity vs uuid v4 vs uuid v7)와 인덱스 지역성 영향
- FK `ON DELETE` 동작이 도메인과 맞는가? (탈퇴 시 리뷰는 cascade인가, 익명화인가?)
- 도메인 규칙의 **DB 이중화**: `CHECK (char_length(content) BETWEEN 10 AND 50)`, `UNIQUE (user_id, place_id)`
- 경합으로 깨지는 규칙(그룹 정원 4)은 DB 제약만으로 막을 수 있는가? 안 되면 어떤 락이 필요한가?
- **인덱스는 쿼리에서 출발한다**: 각 인덱스마다 그것을 쓰는 쿼리를 적었는가? 복합 인덱스 컬럼 순서의 근거는?
- 지도 쿼리(bbox/근처 검색)를 어떤 인덱스로 받을 것인가? (B-tree 복합 / geohash 컬럼 / GiST)
- 카운터(좋아요 수)를 실시간 `COUNT`로 할지, 비정규화할지. 비정규화하면 핫 로우 경합은 어떻게 할지
- 타임스탬프는 `timestamptz`인가?
- 마이그레이션이 되돌릴 수 있는가? 대용량 테이블에 락을 오래 잡는 DDL은 없는가? (`CREATE INDEX CONCURRENTLY`)

### C. 테스트 설계
- 단위(도메인 불변식) / 통합(Testcontainers + 실제 PostgreSQL) / API(WebApplicationFactory) 비율과 이유
- 경계값: 9·10·50·51자, 이미지 3·4장, 정원 3·4·5번째 합류
- **동시성 테스트**: 같은 그룹에 동시에 5명이 합류하는 테스트가 있는가? (`Task.WhenAll` + 실제 DB)
- 테스트 이름이 행동을 설명하는가? (`Join_WhenGroupIsFull_ReturnsGroupFull`)
- 테스트끼리 데이터를 공유해서 순서에 따라 결과가 바뀌지 않는가?
- `test-anti-patterns`가 경고하는 것: 구현 세부를 검증하는 테스트, 과도한 mock

### D. 트랜잭션 경계
- 트랜잭션 안에 외부 I/O(이미지 업로드, 카카오 API)가 없는가? (원본 규칙: 업로드 → URL 확보 → 단일 트랜잭션)
- 경계가 유스케이스 하나와 일치하는가? 부분 커밋 가능성은?
- 격리 수준 선택 근거(Read Committed 기본값으로 충분한가?)와 재시도 정책
